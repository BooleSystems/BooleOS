# ATA, FAT16, and VFS

## Files: open/read/close (ramfs + FAT16)
- `SYS_OPEN (11)`: copies the name from user space via `user_kptr`, allocates the first free slot in `fd_table[proc_slot][0..7]`, and calls `vfs_open` — which tries ramfs via `ramfs_find` and, if not found, FAT16 via `fat16_find`; returns `fd = 3 + idx`, or -1 if not found in either backend or no free slots
- `SYS_READ (5)` with fd≥3: dispatches by `fd->backend` via `vfs_read` — ramfs reads directly from `ramfs_base + offset + pos`, FAT16 uses `fat16_read_at` following the cluster chain; both advance `pos` and return 0 on EOF — non-blocking
- `SYS_CLOSE (12)`: marks the slot as free
- `fd_table[PROCESS_MAX][8]` — global table indexed by process slot; `sys_exit` clears all of the process's fds on exit, avoiding slot leaks
- fds 0/1/2 are reserved (stdin/stdout/stderr); files start at fd=3

## Persistent disk: ATA PIO + FAT16

- `kernel/drivers/ata.c`: ATA PIO driver — probes all 4 possible slots (primary/secondary × master/slave) by sending `IDENTIFY` (0xEC) and discarding ATAPI devices (signature `LBA_MID=0x14`/`LBA_HI=0xEB`); `ata_read_sector`/`ata_write_sector` do LBA28 with `READ SECTORS` (0x20) / `WRITE SECTORS` (0x30) + `CACHE FLUSH` (0xE7); waits for command completion via IRQ14/15 instead of polling when running inside a scheduled process — see "ATA IRQ-driven I/O" below
- `kernel/fs/fat16.c`: reads the BPB from sector 0, caches the whole FAT in the heap (`kmalloc`); `fat16_read_at` follows the cluster chain from an arbitrary offset; `fat16_write_file` frees the old chain, allocates a new one, and rewrites the FAT to disk; `fat16_create`/`fat16_mkdir` look for a free/deleted entry and write an empty dirent (idempotent — doesn't fail if an entry of the matching type already exists). See "Subdirectories" below for `fat16_find`/`fat16_readdir`/`fat16_mkdir`/`fat16_resolve_dir` and the shared lookup machinery they're built on.
- `kernel/fs/vfs.c`: the single dispatcher used by the syscalls — `vfs_open` tries ramfs (read-only, always flat) and then FAT16, resolving a relative path against the caller's `cwd_cluster` (`process_t`, see `docs/scheduler.md`); `vfs_create` calls `vfs_open` first and only creates on FAT16 if not found; `vfs_write` refuses to write to ramfs files. `vfs_fd_t` caches `parent_cluster` + the file's own final path component at open/create time (see "Subdirectories" below) so a later write doesn't depend on the caller's cwd at write time.
- `SYS_CREATE (23)`: open-or-create — copies the name from userland, tries to open it, and if it doesn't exist, creates the entry on FAT16 and returns the fd ready for writing
- Boot: `kmain` calls `ata_init()` right after interrupts are enabled (before the PMM, so the boot failure counter and Safe Mode can use the disk — `docs/safemode.md`) and `fat16_init()` after the scheduler; if there's no disk (or it's not valid FAT16), boot continues normally and on-disk file operations return -1 without crashing
- `tools/make_disk.sh` + the `make disk` target: generates `build/disk.img` (32 MB, FAT16 via `mkfs.vfat`) only if it doesn't already exist, preserving data across builds; `make run` (the `tools/Makefile` target) attaches the disk as `-drive file=build/disk.img,format=raw,if=ide`
- Shell: `touch <name>` creates an empty file (`SYS_CREATE` + `SYS_CLOSE`); `ls [dir]` lists ramfs and FAT16 separately, defaulting to the shell's cwd; `mkdir <dir>` creates a directory (`SYS_MKDIR`); `cd [dir]` changes the shell's cwd (`SYS_CHDIR`; no argument goes to the root). `touch`/`edit`/`ls`/`mkdir`/`cd` all accept a path with a subfolder (e.g. `touch docs/notes.txt`) — `touch`/`edit` need no code of their own for this, since they just forward whatever string was typed straight to `SYS_CREATE`/`SYS_OPEN`, and path resolution happens entirely on the kernel side (see "Subdirectories" below)
- Editor: `load_file` now creates the file (`SYS_CREATE`) when it doesn't exist, keeping the fd open; Ctrl+S writes the whole buffer via `SYS_WRITE_FILE` and shows "saved" or "saved (no disk)" in the footer; Ctrl+Q closes the fd before exiting

## Subdirectories (Phase 15)

FAT16 has two structurally different kinds of directory, and the design here treats that difference as the central fact to get right (see the out-of-bounds history below for why glossing over structural differences in this file has bitten the project before):

- **The root directory** is a fixed-size region at a fixed LBA (`g_root_start_lba`/`g_root_sector_count`, derived from the BPB's `root_entry_count`) with no cluster chain and no `.`/`..` entries. It can't grow past its fixed size.
- **A normal subdirectory** is an ordinary dirent with `ATTR_DIRECTORY` set, whose `first_cluster` starts a regular FAT chain — exactly like a file's data, including growing by allocating another cluster when full. Every subdirectory's first sector holds two special entries: `.` (points to the subdirectory's own first cluster) and `..` (points to the parent's first cluster, or `0` if the parent is the root — standard FAT16 convention, since the root has no cluster of its own to point to). The root itself has no `.`/`..` entries, so `cd ..` from the root fails (nothing above the root) and `cd .` at the root fails too (no literal `.` entry exists there) — both are accepted, standard FAT16 limitations, not bugs.

**Shared lookup machinery** (`kernel/fs/fat16.c`) — added specifically to avoid repeating the Phase 10 duplicated-lookup bug (see below) now that there are many more places that could walk a directory:

- `dir_iter_t` / `dir_iter_next_sector()`: the one place that knows how to step through a directory's sectors, whether that means the fixed root region or a FAT chain. Every scan in the file goes through this.
- `dir_lookup()`: the one place that builds the combined 11-byte name (`name[8]` + `ext[3]`) and compares it — used to find an entry by name in any directory, root or not, file or subdirectory.
- `dir_insert()`: the one place that finds a free/deleted slot and writes a new dirent, extending (allocating + zeroing) a subdirectory's chain if it's full (the root still just fails when full, as before) — shared by `fat16_create` and `fat16_mkdir`.
- `resolve_path()`: walks a `"/"`-separated path component by component via `dir_lookup()`, stopping right before the final component, and returns the cluster of the directory that contains it (0 = root) plus that final component's 8.3 name. An absolute path (starting with `/`) always resolves from the root; a relative path resolves against a caller-supplied `dir_cluster` (the process's `cwd_cluster`, see `docs/scheduler.md`). `fat16_find`, `fat16_create`, `fat16_mkdir`, and `fat16_resolve_dir` are all thin wrappers around this plus one final `dir_lookup()`/`dir_insert()` call, each interpreting the result differently (a file, an insert target, a directory-only match).
- A freshly allocated cluster is explicitly zeroed sector-by-sector **before** `.`/`..` are written into it (`fat16_mkdir`) — a cluster reused from a previous file/directory carries whatever was there before, and without this, `dir_lookup`/`fat16_readdir` could misread that leftover data as real dirents the first time the new directory is scanned.
- Name-collision policy: `fat16_create` fails if a *directory* already exists under that name (this couldn't happen before this phase, since directories didn't exist); symmetrically, `fat16_mkdir` fails if a *file* already exists under that name. Both remain idempotent when an entry of the *matching* type already exists — the same discipline `fat16_create` always had, now extended to types.
- `fat16_write_file(parent_cluster, name, buf, len)` takes an already-resolved parent directory cluster and a single final path component (no `/`) rather than a full path — the caller (`vfs_write`, via the fd's cached `parent_cluster`/`name`) already knows exactly where the entry lives from when the file was opened/created, so a write never needs to re-walk a path or depend on the calling process's cwd at write time (which could have changed via `cd` since the file was opened).
- `SYS_CHDIR`/`SYS_MKDIR` and `SYS_READDIR`'s new optional path argument are documented in `docs/syscalls.md`; `cwd_cluster` (`process_t`) and its inheritance across both `fork()` and `exec()` (`run`/`edit`) are documented in `docs/scheduler.md`.
- **A program launched via `run`/`edit` resolves relative paths against the launching process's cwd, not always the root.** This was found missing during Phase 15's own manual test: `edit`/`run` go through `exec()`, which spawns a brand-new process (`process_spawn_user()`) rather than forking the caller, so the `cwd_cluster` inheritance wired into `process_fork()` didn't cover it. `exec()` now takes an explicit `cwd_cluster` parameter, and `SYS_EXEC` passes the calling process's own `cwd_cluster` — see `docs/scheduler.md` for the full chain.
- **`to_8_3()` must find the real `.` in the original string before deciding a name has no extension — it can't just stop wherever the 8-char base cap happens to land.** The base-name loop still stops at 8 characters or a `.`, whichever comes first, but if it stopped at 8 (not a `.`), it now keeps scanning ahead (without writing) until it either finds the real `.` or reaches the end of the string. Skipping this second scan was a real, found-during-testing bug: for a base longer than 8 characters whose `.` comes after that point (e.g. `"selftest_tmp.txt"`, base `"selftest_tmp"` is 12 chars), the loop's stopping point (`'_'`, at index 8) was never `.`, so the extension was silently dropped entirely — producing `"SELFTEST"` instead of `"SELFTEST.TXT"`. **This also means two names that are visually different in their long form can still collide on the exact same on-disk 8.3 entry** if they share both their first 8 characters and their extension — a real, inherent FAT 8.3 limitation (case-insensitive, 8+3 truncated), not something code can "fix" away. `"selftest_tmp.txt"`/`"selftest_sub.txt"`/`"selftest_fork_marker.txt"` all shared `"selftest"` + `"txt"` and packed to the identical `SELFTESTTXT`, which is exactly what caused `user/selftest.c`'s own subdirectory-isolation test to see a false leak — see `docs/testing.md` for how those test filenames were fixed (renamed to genuinely 8.3-distinct names), not by changing `to_8_3()` further.

## Later FAT16 changes (Phase 17)

- `fat16_init()` rejects a BPB with `sectors_per_cluster == 0` (printing the reason) before it is used as a divisor.
- `fat16_write_file()` refuses a directory entry (`ATTR_DIRECTORY`) and no longer re-reads the dirent sector `dir_lookup()` just left in `dir_buf`.
- **`vfs_write()` is a stream write, `vfs_write_all()` the whole-file replace.** `SYS_WRITE` on a FAT16 fd goes through `vfs_write()` → `fat16_write_at()` at `fd->pos` (advancing it), so consecutive writes accumulate; before, every 128-byte chunk replaced the whole file and only the last survived. `SYS_WRITE_FILE` ("save this buffer as the file", used by the editor) goes through `vfs_write_all()` → `fat16_write_file()`.
- `fat16_write_at(parent_cluster, name, pos, ...)`: positional write that grows the cluster chain as needed. The dirent is looked up fresh on every call (a stale cached `fd->first`/`fd->size`, e.g. after a truncate, is harmless), `pos` must be ≤ the current size (no sparse files), the FAT is flushed only when the chain grew, and data goes to disk first, then the FAT, then the dirent, so an I/O failure never leaves a dirent claiming more than was written.
- `fat16_get_path(cluster, out, size)` (for `pwd`/`SYS_GETCWD`): rebuilds a directory's absolute path by walking up through each `..` entry and finding the child's name in its parent (`dir_find_child_name()`); names are 8.3 uppercase via the shared `dirent_display_name()` (also used by `fat16_readdir()`); depth capped at `FAT16_PATH_MAX_DEPTH` (16) to survive a corrupted `..` chain; the root needs no disk access.
- **Known limitation:** `dir_buf` and `sector_buf` are single global buffers shared by every FAT16 caller and held across blocking `ata_write_sector()` calls, so a concurrent FAT16 call from another process can clobber them. The fix is the whole-operation FAT16 lock of ROADMAP Phase 28.

## ATA IRQ-driven I/O

- Replaces phase 10's busy-wait: whenever `ata_read_sector`/`ata_write_sector` run inside a scheduled process, they block the calling process instead of polling `BSY`/`DRQ` while a disk command is in flight; the original polling path is kept as a fallback for calls with no current process (early boot, e.g. `fat16_init()` reading the BPB before the scheduler ever runs a process)
- IRQ14 (primary channel, vector 46) and IRQ15 (secondary, vector 47) stubs were added to `isr.asm`/`idt.c` following the existing IRQ0/IRQ1 pattern; `ata_init()` registers the handler and unmasks the correct line — plus the master PIC's IRQ2 cascade, required for any slave-PIC IRQ to reach the CPU — for whichever channel was actually detected
- `ata_irq_handler()` is intentionally minimal: it acknowledges the drive's IRQ (reading Status clears the line) and flips the waiting process back to `PROCESS_READY`; it never touches the scheduler or performs a context switch itself
- `ata_wait_irq()`: `cli` → check an "IRQ already fired?" flag → if not yet fired, mark the process `PROCESS_BLOCKED` and call `scheduler_block_current()`. The check and the block happen inside the same `cli`/`sti` section, so an IRQ that fires before the process finishes blocking is never lost — it's just observed as "already fired" instead
- Exclusion gate (`ata_gate_acquire`/`ata_gate_release`): since the calling process no longer holds the CPU for the whole operation, a second process could otherwise issue a competing ATA command on the same registers while the first is still waiting on its IRQ. The gate serializes access; a second process waiting for the gate also blocks for real via `scheduler_block_current()` (no busy-wait), rechecking the gate after being woken since more than one waiter can be released at once
- New process state `PROCESS_BLOCKED` (`process.h`) — kept distinct from `PROCESS_SLEEPING` so the timer's tick-based wake-up (`process_wake_sleepers`) never touches it — and `scheduler_block_current()` (`scheduler.c`), a sibling of `scheduler_yield()` that switches away from the CPU without forcing the state back to `READY`; whoever owns the wait (the IRQ handler, or the process releasing the gate) is responsible for that transition
- Both the IRQ handler and the gate re-check that a waiter is still `PROCESS_BLOCKED` before waking it, so a process killed (`kill <pid>`) while waiting can't have its (possibly already reused) process-table slot resurrected by a late wake-up
- `probe()`, disk detection, `fat16.c`, and `vfs.c` are unchanged
- **`g_irq_fired` is reset the moment a new command is issued (`outb(REG_CMD, ...)`), not just when a wait for one finishes** — found and fixed during Phase 15's own testing, as an intermittent (timing-dependent) bug, not a Phase 12 regression that had ever been exercised this way before. The drive raises a real completion IRQ for *every* command, including the ones serviced by the early-boot polling fallback above (`fat16_init()`'s ~65 BPB/FAT reads, run before any process exists) — but that polling path never calls `ata_wait_irq()`, the only place that used to consume `g_irq_fired`. Left dirty like that, a *later*, genuinely IRQ-driven wait could see that stale "already fired" and skip waiting for its own command's real completion, checking `DRQ` before the drive was actually ready — intermittently, depending on whether the drive happened to already be ready by coincidence. Resetting the flag at command-issue time (in both `ata_read_sector` and `ata_write_sector`, for `CMD_READ`/`CMD_WRITE`/`CMD_FLUSH` alike) means no leftover signal from any prior command — polled or IRQ-driven — can be mistaken for the one just issued.
